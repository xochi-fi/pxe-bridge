# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

JSON-RPC bridge that connects EVM intent solvers to Aztec L2 shielded settlement. Runs an HTTP server wrapping Aztec SDK operations via an embedded PXE wallet. Supports both standard Schnorr accounts and a custom spending-limit account contract (Noir) with on-chain per-tx caps, daily volume limits, recipient allowlist, and timelocked admin.

```
EVM Solver --JSON-RPC--> pxe-bridge --Aztec SDK--> Aztec L2 Node
```

## Commands

```bash
npm install              # install dependencies
npm run build            # tsc compile to dist/
npm run typecheck        # tsc --noEmit for src/ and (via tsconfig.test.json) tests/ and scripts/
npm test                 # vitest run (unit + integration)
npm run test:watch       # vitest in watch mode
npm run test:coverage    # vitest with v8 coverage
npm run test:e2e         # e2e tests (requires running Aztec sandbox)
npm run test:e2e:up      # docker compose up, run e2e, compose down
npm run dev              # run with tsx (no build step)
npm start                # run compiled dist/index.js
npm run bridge-fee-juice -- --recipient 0x<addr>   # bridge fee juice from L1, print FEE_JUICE_CLAIM (Schnorr only)
npm run bridge-fee-juice -- --deployer --recipient 0x<addr>   # same, printed as PXE_BRIDGE_DEPLOYER_FEE_JUICE_CLAIM
npm run bridge-fee-juice -- --wait 0x<messageHash>   # resume a timed-out wait; never rerun the bridge step
npm run bridge-fee-juice -- [--deployer] --recipient 0x<addr> --recover <deposit file>   # find a deposit whose run died; same --deployer as the lost run, or the claim prints under the wrong variable
npm run bridge-fee-juice -- [--deployer] --address-only   # dev: derive the address from PXE_BRIDGE_SECRET_KEY, offline
npm run top-up-fee-juice # bridge + claim on an account's behalf (spending limit account); env only, refuses arguments
npm run update-allowlist -- --add 0x<addr> --index <n>   # add one allowlist recipient
npm run update-allowlist -- --revoke 0x<addr>            # revoke one allowlist recipient
npm run admin -- status [--expect-root <hex>] [--expect-paused] [--min-fee-juice <n>]   # exit bits 2 pause, 4 proposal, 8 root, 16 fee juice
npm run admin -- pause|unpause|apply-limits|cancel-limits
npm run admin -- propose-limits --max-per-tx <n> --daily <n>
```

Admin commands read `SPENDING_LIMIT_ACCOUNT`, `SPENDING_LIMIT_ADMIN_KEY` (not needed by `status`) and `AZTEC_NODE_URL`; `update-allowlist` also `PXE_BRIDGE_ALLOWLIST_SEED` and `PXE_BRIDGE_ALLOWLIST_RECIPIENTS`, which `status` uses for the expected root when `--expect-root` is absent. All need the artifact in `contracts/spending_limit_account/target/`.

CI runs `typecheck` -> `test` -> `build`, then a separate `e2e` job via docker compose.

## E2E Tests

E2e tests (`tests/e2e/`) run against a real Aztec sandbox node via `docker-compose.yml` (Anvil L1 + Aztec node). The `globalSetup` auto-starts compose if `AZTEC_NODE_URL` is not set.

Anvil runs with `--block-base-fee-per-gas 0`, which it holds constant. With a nonzero base fee the L2 min fee steps down 3-15x at each L1 fee oracle refresh, and a send priced off `getPredictedMinFees` right after a checkpoint is simulated against the previous, higher fee and rejected. CI starts compose itself and dumps `docker compose logs` on e2e failure.

The compose default runs the `linux/amd64` Aztec image, which fails under ARM emulation (barretenberg SIGILLs, or the node times out connecting to its bb socket). E2e tests are authoritative on CI (ubuntu x86_64). On Apple Silicon, overriding the image to `platform: linux/arm64` (`aztecprotocol/aztec:5.1.0` ships an arm64 variant) has started locally and run `tests/e2e/deployer-claim.test.ts` to a pass, but it is flaky: startup has also timed out on the bb socket while the host was heavily loaded. Treat local arm64 runs as best effort.

## Architecture

Twelve TypeScript source files plus a Noir contract, no framework -- plain `node:http` server with zod validation:

- **`index.ts`** -- Entrypoint: reads env, resolves secret key (via `secrets.ts`), validates port range, warns if API key unset, parses `FEE_JUICE_CLAIM` and `PXE_BRIDGE_DEPLOYER_FEE_JUICE_CLAIM` (the latter refused without spending-limit config), validates `PXE_BRIDGE_ALLOW_SPONSORED_FPC` and logs whether the SponsoredFPC deployment fee fallback is on, constructs spending limit config if admin address is set, creates `AztecClient`, starts server bound to `PXE_BRIDGE_HOST`.
- **`secrets.ts`** -- Secret key resolution: AWS Secrets Manager fetch (via `PXE_BRIDGE_SECRET_ARN`) or env var fallback (`PXE_BRIDGE_SECRET_KEY`, dev only). Rejects env var when `NODE_ENV=production`. Supports plain hex and JSON `{"key":"..."}` secret formats. Validates the key is 32 bytes and below the BN254 Fr modulus; roughly 81% of random 32-byte values are not, so this rejects at startup with a named cause rather than deep in the SDK at connect time.
- **`server.ts`** -- HTTP server factory (`createApp(client, opts?)`). Auth (Bearer token, constant-time compare), Content-Type enforcement (CSRF defense), rate limiting (60 req/min sliding window), body size limit (64KB), a 30s deadline on receiving a request (`server.requestTimeout`) and a 150s deadline on producing a response (`res.setTimeout`, above the client's 120s tx timeout). The two are separate: `requestTimeout` alone, which is what this used to be, bounds nothing about how long a reply can take. Also serves `POST /admin/resume`, gated on `PXE_BRIDGE_ADMIN_KEY` and 404 when that is unset. Validates the `Idempotency-Key` header (1-128 printable ASCII, rejected rather than sanitised) into `RpcContext`. Accepts `IAztecClient` interface for testability.
- **`rpc.ts`** -- JSON-RPC 2.0 dispatch. Method switch: `aztec_createNote` -> `handleCreateNote`, `aztec_getVersion` -> `handleGetVersion`. Sanitizes internal errors before returning to caller. Uses `null` id for invalid envelopes per spec. A `PostSubmissionError` commits the reservation rather than releasing it, and answers with a distinct message plus `error.data.txHash`: the transfer may be on chain, so the caller must reconcile rather than retry.
- **`aztec-client.ts`** -- `AztecClient` class implementing `IAztecClient`, wrapping Aztec SDK v5. Creates `EmbeddedWallet`, derives account from secret key (SHA-256 domain-separated salt, reduced into the BN254 field -- a raw digest exceeds the modulus ~81% of the time). When `spendingLimitConfig` is provided, creates a `SpendingLimitAccountContract` via `AccountManager.create()`, registers artifact with PXE, stores in WalletDB, and patches `getAccountFromAddress` for tx routing; otherwise uses standard Schnorr account. Deploys account contract on first connect, caches `TokenContract` instances (capped at 100). The deployment fee comes from `FEE_JUICE_CLAIM` for the plain Schnorr account, otherwise from SponsoredFPC, gated by `sponsoredFpcSetting()` (`PXE_BRIDGE_ALLOW_SPONSORED_FPC`, off under `NODE_ENV=production` by default): refused with `SPONSORED_FPC_REFUSED_ERROR` naming the account, before anything is registered or sent. The spending-limit account cannot self-deploy, so `ensureDeployer()` first deploys a plain Schnorr deployer derived from the same master secret under salt `baseSalt + 1` (same signing key, stable address, no extra key material; `deriveDeployerKeys()` is the one derivation, shared with `scripts/bridge-fee-juice.ts --deployer`). With `PXE_BRIDGE_DEPLOYER_FEE_JUICE_CLAIM` the deployer self-deploys via `FeeJuicePaymentMethodWithClaim` and then sends the account's deployment with no payment method, which `BaseWallet.completeFeeOptions` turns into `PREEXISTING_FEE_JUICE` for the sender, so the deployer's balance pays both; without it, a deployer whose balance funds a deploy pays both from it (`funded`; where SponsoredFPC is permitted the balance must cover the per-tx gas limit at the deploy's max fees, so a dust deposit cannot steer the deploy off SponsoredFPC), else both go via SponsoredFPC. Whether the deployer exists is read from its initialization nullifier (`getContractMetadata`), not publication, since a self-deploy leaves it unpublished and a retry would otherwise resend a spent claim. With the deployer already initialized and the claim's message unspent (nullifier looked up from the recomputed FeeJuice message hash, `feeJuiceMessageHash`, whose L1 sender is `FEE_JUICE_ADDRESS` since the Inbox rewrites the portal's), the account deploy consumes the claim instead, as `FEE_JUICE_WITH_CLAIM` with the deployer as sender and fee payer; with it spent, the deployer pays `PREEXISTING_FEE_JUICE` (`limitAccountFeePath`). An uninitialized deployer has its claim checked before the send: no message throws naming the claim, and a spent claim self-deploys from the deployer's balance (`NO_FROM` with no payment method, which `AccountEntrypointMetaPaymentMethod` makes `PREEXISTING_FEE_JUICE`) or, with a zero balance, throws naming the spent claim. The node's insufficient-balance rejection is rethrown naming the deployer; there is no precheck, since the declared fee limit comes from `EmbeddedWallet.sendTx`'s own gas estimate. An `Existing nullifier` on the deployer's own deploy, or on the account's, counts as success only if that contract then reads INITIALIZED; a spent fee claim's message nullifier fails the send the same way. The deployer claim is refused without `spendingLimitConfig` (`DEPLOYER_CLAIM_WITHOUT_SPENDING_LIMIT_ERROR`). Calls `assertAllowlistRootCurrent()` before each `createNote` when spending limits are active, which reads `get_allowlist_root` and refuses to send if the configured tree does not reproduce it; nothing is pushed onto the contract before a send, since the entrypoint derives the declared amount, the recipient and the membership witness from the payload it signs. Account deploys carry `DEPLOY_FEE_HEADROOM` over the worst predicted base fee. Secret key zeroed from memory after connect. Transaction timeout of 120s. Logs the derived account address on connect, because the spending-limit account cannot obtain fee juice for itself and topping it up means naming that address. Exports `deriveAccountKeys()`, which the operator scripts use so they cannot drift from the address the bridge deploys, and refuses `feeJuiceClaim` together with `spendingLimitConfig` (see `FEE_CLAIM_WITH_SPENDING_LIMIT_ERROR`).
- **`fee-juice.ts`** -- Bridging fee juice from L1 and claiming it on another account's behalf. Exists because the spending-limit account cannot acquire fee juice itself: its entrypoint admits exactly one call and requires it to be `transfer_to_private` on the pinned token, and every fee payment method contributes a second call to the same AppPayload (`mergeExecutionPayloads`), so `PREEXISTING_FEE_JUICE` is its only fee branch. `FeeJuice.claim(to, ...)` names its beneficiary in an argument rather than taking `msg_sender`, so a funded payer can credit the account. `bridgeFeeJuice()` generates the claim secret itself and hands it to `onSecret` before any L1 write, then deposits on L1 (approve + `depositToAztecPublic`, not the SDK's `bridgeTokensPublic`, which returns the secret only with the receipt, so a run killed after broadcast lost the deposit), hands the claim and its message hash to `onClaim` before waiting for the message, then returns the claim; the L1 deposit cannot be undone, so a wait that times out must not take the only copy with it. `recoverFeeJuiceClaim()` rebuilds the claim from what `onSecret` recorded by scanning the portal's `DepositToAztecPublic` events to the recipient (`to` is the only indexed field; amount and secret hash are matched client-side) from the recorded L1 block; on a miss, the recorded L1 sender's latest and pending nonces say whether the deposit can still land or bridging anew is safe. `writePendingDeposit()` / `findPendingDeposit()` persist what `onSecret` receives to an owner-only `fee-juice-deposit-<secretHash>.json` in the working directory, which the scripts write before any L1 write, add the landed claim to, and delete only once the claim is safe: message synced (`bridge-fee-juice`) or claim transaction succeeded (`top-up-fee-juice`). `recordBridgedClaim()` adds the claim by write-and-rename; `bridgedClaimOf()` reads it back, so recovery from an enriched file skips L1. `topUpFeeJuice()` does bridge, wait, claim. `scripts/bridge-fee-juice.ts` and `scripts/top-up-fee-juice.ts` are thin CLIs over these, and `tests/e2e/helpers.ts` drives the same functions against the sandbox. `bridge-fee-juice` takes the recipient as an address (`--recipient`), so production needs no secret key to bridge; deriving it from `PXE_BRIDGE_SECRET_KEY` is dev only and offline. `top-up-fee-juice` pays from a separate payer (`FEE_JUICE_PAYER_KEY`) or from the deployer (`FEE_JUICE_PAYER_DEPLOYER=true`, key via `resolveSecretKey`), checks the payer by its init nullifier since the deployer is unpublished, opens its wallet stores under `os.tmpdir()` and deletes them on exit, SIGINT, SIGTERM and SIGHUP (SIGKILL or a crash leaves them), and resumes from `FEE_JUICE_RESUME_CLAIM` without a second deposit. There is no `transfer` on FeeJuice, so an existing L2 balance cannot be moved and every top-up starts on L1.
- **`types.ts`** -- Zod schemas, TypeScript types, `IAztecClient`, and `PostSubmissionError` (here, not in `aztec-client.ts`, so `rpc.ts` can narrow on it without importing the Aztec SDK). `CreateNoteResult` returns `noteHashes`/`nullifiers` in full; the scalar `noteCommitment`/`nullifierHash` are deprecated aliases for index 0, since a `transfer_to_private` emits two note hashes and three nullifiers and `nullifiers[0]` is the protocol nullifier. Addresses validated as 32-byte hex (64 chars). Amounts validated as non-negative integers without leading zeros, capped at 78 digits (uint256 max). Includes optional XIP-1 trade context fields (`tradeId`, `subTradeIndex`, `totalSubTrades`) -- all three must be provided together or all omitted.
- **`limits.ts`** -- `TransactionLimits` class: per-tx ceiling (`PXE_BRIDGE_MAX_AMOUNT`), 24h rolling volume cap with circuit-breaker (`PXE_BRIDGE_DAILY_LIMIT`), configurable cooldown delay for large transfers. Checked before every `createNote`. Application-level defense-in-depth; on-chain limits (Phase 2) enforce independently. The breaker trips only when committed volume reaches the cap; a single request larger than the remaining budget is rejected on its own, since tripping there let one oversized request stop the bridge for a full window. `restore()` seeds the window from the audit log at startup.
- **`audit.ts`** -- `AuditLogger` class: JSON-lines structured logging of every `createNote` call. Five statuses: `submitting` (intent, written before the send), then `success`, `rejected`, `error`, or `unknown`. `unknown` is distinct from `error` because "may have moved funds" and "moved nothing" need opposite responses on replay. Writes to file (`PXE_BRIDGE_AUDIT_LOG`) or stdout with `[audit]` prefix. `replayAuditLog()` rebuilds both durable stores in one pass -- the rolling window and the idempotency keys -- so a restart forgets neither; it tolerates a truncated final line rather than refusing to start.
- **`idempotency.ts`** -- `IdempotencyStore`: replay cache keyed on the `Idempotency-Key` header, 24h TTL. `begin()` claims synchronously so concurrent duplicates cannot both proceed; `settle()` records what a retry should replay; `abandon()` frees a key whose request moved nothing, which deliberately departs from Stripe (a recorded error would strand the caller with no way to settle the trade). Stores the outcome rather than the whole response, so a replay answers under the retrying request's own JSON-RPC id.
- **`allowlist-tree.ts`** -- The allowlist, as the bridge holds it. Builds a dense height-10 Merkle tree whose leaves are commitments `h(recipient, salt)`, derives a membership witness per recipient, and exports `rootFromSiblingPath()` as the mirror of the circuit's verification. Salts derive from one secret seed rather than being stored per leaf: they have to be secret, since addresses are enumerable and a publicly derivable salt would let anyone recompute a leaf and test candidates against it. Dense because per-leaf salts leave no canonical empty subtrees to short-circuit, which is what bounds the height at 10 rather than something larger -- building costs `2^height` hashes, 0.33s here against 21s at height 16. Four hash values are pinned identically here and in `main.nr`, because the two implementations never meet at runtime and drift would surface only as every transfer reverting.
- **`spending-limit-account.ts`** -- Custom Aztec account contract TypeScript wrapper. `SpendingLimitAccountContract` implements `AccountContract` with a custom entrypoint that includes declared amount/recipient in the signed hash via `poseidon2HashWithSeparator`. The entrypoint derives the amount, the recipient AND the membership witness from the `transfer_to_private` call in the payload it is signing, so declared == actual holds by construction and there is no per-call state for a concurrent send to overwrite. The tree lives in a holder shared by reference with every entrypoint, since `getAccount()` is called afresh on every wallet resolution and is not memoized, so per-instance state is written to an orphan while a sibling entrypoint signs. Sharing one tree across concurrent sends is safe: the witness is unsigned, the leaf is rebuilt from the signed recipient, and the root is revalidated against live storage at inclusion time. `loadSpendingLimitArtifact()` loads the artifact without a signing key, for the operator scripts. Used with the Noir contract in `contracts/spending_limit_account/`.
- **`contracts/spending_limit_account/`** -- Noir account contract (compiled with `aztec compile`, not `aztec-nargo compile` -- the latter is a symlink to plain `nargo`, ships no transpiler, and emits `transpiled: false`, which `loadContractArtifact` rejects). Extends Schnorr with `check_spending_public`: per-tx cap, 25-bucket sliding daily window, a Merkle recipient allowlist compared as one root, single permitted token, timelocked `propose_limits`/`apply_limits`. The allowlist is one storage slot: membership is proven in private against a root and public only checks that root, so the set never goes on chain. `update_recipient` is the whole allowlist API, taking `(index, old_leaf, new_leaf, sibling_path)`; it verifies the path against the current root before recomputing, which constrains it to one leaf per call. Every call publishes its sibling path. The admin key alone can rewrite any position touched by a published `update_recipient`, and that position's sibling (`index ^ 1`); the seed protects only positions that are neither (#32). It is untimelocked, deliberately: the contract cannot tell addition, removal and substitution apart, so one policy has to cover all three, and the 24h notice bought public legibility that a secret set does not have while costing revocation latency. `pause`/`unpause` remains the immediate emergency stop against a compromised signing key, checked in `check_spending_public` so it bites at inclusion time. Every root change invalidates in-flight transactions, additions included; there is no grace window, because accepting a superseded root would also mean accepting a revoked recipient. Artifact is built into `target/` by the `contract` CI job and gitignored, not committed. Must match Aztec SDK version (currently v5.1.0, set in `Nargo.toml`).

  Because the artifact is rebuilt every CI run, `scripts/contract-class-id.js` pins its contract class ID against `contracts/spending_limit_account/CLASS_ID`. The class ID feeds address derivation, so toolchain drift would otherwise move the account address silently: the bridge would find nothing there, deploy a fresh empty account, log "Ready", and strand the balance at the old address. Any deliberate change to `main.nr` moves the class ID, so `CLASS_ID` has to be updated in the same commit. The check warns instead of failing while `CLASS_ID` is absent, since the value can only be produced by an x86 CI run (`aztec compile` does not finish on ARM). To re-baseline after a deliberate contract change, download the `contract-artifact` from the CI run into `target/` and run `node scripts/contract-class-id.js`. CI compiles with `HARDWARE_CONCURRENCY=1`: otherwise `bb aztec_process` derives the private functions' verification keys concurrently, which bb 5.1.0 is not thread-safe for, and the constructor VK, and with it the class ID, intermittently comes out wrong.

- **`scripts/admin.ts`, `scripts/update-allowlist.ts`** -- Admin CLIs over `scripts/spending-limit-admin.ts`, which holds the shared parts: admin self-deploy (`npm run admin -- deploy`, paid from `FEE_JUICE_CLAIM`; deploying by running the bridge with the admin key would persist it in `./aztec-wallet-data`), admin derivation via `deriveAccountKeys`, an `EmbeddedWallet` with `proverEnabled`, and a send that prints the tx hash before waiting for the receipt. `ephemeral: true` alone still writes the wallet and PXE LMDB stores, admin key included, to `os.tmpdir()` and never deletes them, so `connectAdmin` and `deployAdmin` open both stores themselves and `runScript` deletes them on exit, on a throw and on SIGINT/SIGTERM (not SIGKILL). Keys and the seed are read with `takeSecretEnv`, which deletes them from `process.env`, and range-checked via `secrets.ts` `validateKey` before the SDK sees them, since the SDK's range error prints the value. `status` reads public storage with `node.getPublicStorageAt` at the slots in the artifact's `storageLayout`, because the contract has no getters for limits, pause or the pending proposal; `readAccountState` refuses unless `node.getContract(account)` has the artifact's class ID, since another version's layout would decode the wrong slots. Every field it reads packs to one Field; a `PublicImmutable` holds its value at its slot and a hash at the next. The node is trusted: no public-data witness. Exit bits (1 alone error; 2 pause state not expected, `--expect-paused` inverts; 4 proposal pending; 8 root not expected; 16 admin fee juice below `--min-fee-juice`) back a cron alert. Sends refuse unless the key derives the on-chain admin; `update-allowlist` also unless the configured set reproduces `allowlist_root`. `pause` is checked only in `check_spending_public`, so a compromised signing key can still burn fee juice on reverting transactions while paused.

## Security

- Binds to `127.0.0.1` by default -- set `PXE_BRIDGE_HOST=0.0.0.0` only behind a reverse proxy
- API key auth via `Authorization: Bearer <key>` -- required for production
- `Content-Type: application/json` required on POST (blocks browser CSRF without CORS headers)
- Secret key fetched from AWS Secrets Manager in production (env var rejected)
- Secret key zeroed from memory after wallet derivation
- On-chain spending limits via custom Noir account contract (per-tx cap, daily volume, Merkle recipient allowlist, timelocked limits)
- The recipient allowlist is a secret set. Only its root is on chain, membership is proven in private, and the salts that make leaves unguessable derive from an operator-held seed
- Fee juice top-up needs a payer key but adds no trusted party: the L1->L2 message commits to its beneficiary, so a claim can only credit the account it was bridged to
- Production spending-limit deploy, no SponsoredFPC: (1) start the bridge once with no claim; it logs `Account address` and `Deployer address` and stops at the SponsoredFPC refusal before sending; (2) `npm run bridge-fee-juice -- --deployer --recipient <Deployer address>` prints `PXE_BRIDGE_DEPLOYER_FEE_JUICE_CLAIM` and the message hash, then waits (`--wait <messageHash>` resumes; the claim secret is written to an owner-only `fee-juice-deposit-<secretHash>.json` before the deposit, the landed claim is added to it, and it is deleted only once the message has synced; `--deployer --recipient <Deployer address> --recover <file>` recovers a run that died; rerunning deposits twice); (3) start the bridge with that claim, wait for `Ready`; (4) `FEE_JUICE_PAYER_KEY` set (via `read -s` or `op run`, never inline) to a separately bootstrapped plain Schnorr payer, then `npm run top-up-fee-juice` to the logged `Account address` for transfer fees. `FEE_JUICE_PAYER_DEPLOYER=true` (pay from the deployer's leftover balance) is refused under `NODE_ENV=production`, because the deployer key is the bridge's signing key and the script would load it onto the operator's machine. `FEE_JUICE_PAYER_DEPLOYER`, `FEE_JUICE_MINT` and `FEE_JUICE_PAYER_SPONSORED` accept only `true`/`false`, and `FEE_JUICE_PAYER_SPONSORED=true` is gated by the same policy as `PXE_BRIDGE_ALLOW_SPONSORED_FPC`. The top-up deposit file likewise keeps the claim until the claim transaction succeeds
- Rate limiting: 60 RPC requests/min sliding window
- Response headers: `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`
- Docker: runs as non-root (`USER node`), `npm ci` for reproducible builds, source maps stripped

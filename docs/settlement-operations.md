# Settlement operation contract (`pxe-bridge.settlement.v2`)

Consumer: axol-io/Riddler. Decisions D-A (single-use may-broadcast), D-B
(legacy migration) and D-C (term encodings) are from xochi
`docs/planning/shielded-execution.md` §7.

## Versions

| Version | Change | Status |
| --- | --- | --- |
| `pxe-bridge.settlement.v1` | #45 | retired: both methods answer `-32602`, `data {reason: "settlement_version_unsupported", supported: "pxe-bridge.settlement.v2"}` |
| `pxe-bridge.settlement.v2` | #78: mined observations carry `partialNoteRandomness` | current |

The request shape, encodings and fingerprint (domain
`pxe-bridge/settlement-fingerprint/v1`) are unchanged in v2, so an operation
journaled under v1 keeps its fingerprint. Riddler requires a non-null
`partialNoteRandomness` before it treats a finalized success as delivered;
`null` holds the obligation.

## Methods

| Method | Params | Answer |
| --- | --- | --- |
| `aztec_createNote` | one object: `version: "pxe-bridge.settlement.v2"`, `operationId` (1-128 printable ASCII, MUST equal the `Idempotency-Key` header), `network` (§7 `NetworkIdentity`), `corridor {corridorId, corridorRevision, manifestDigest}`, `accountMode` (`spending_limit` \| `standard`), `recipient`, `recipientDescriptorDigest`, `token`, `amount`, `validUntil` (unix seconds). Encodings: "Frozen encodings" below. Unknown keys refused. | `result {version, operationId, fingerprint, observation}` for `pending`/`included`/`finalized`/`reverted`; otherwise a JSON-RPC error below. |
| `aztec_getSettlement` | `{version, operationId}` | `result {version, operationId, found, fingerprint?, terms?, state?, attempts?: [{attempt, txHash, expirationTimestamp, mayBroadcast}], observation, journal {writable, reason?, detail?}}`. Read-only; served while journal writes are disabled. `found: false` answers `observation {state: "unknown", reason: "operation_not_journaled"}`: absence never means "no payout". |

Send `aztec_getSettlement` to `POST /api/recovery` with Bearer
`PXE_BRIDGE_RECOVERY_API_KEY` for reserved reconciliation capacity (disabled
when that credential is unset). `/` and `/api/rpc` accept it with
`PXE_BRIDGE_API_KEY` under ordinary capacity.

Legacy `{recipient, token, amount, chainId, ...}` params are refused
(`-32602`, `data.reason: "legacy_params_refused"`). The wire enum keeps
`standard` for decoding, but hard readiness admits new work only when
`accountMode` is `spending_limit` and the deployment record is present.

## Frozen encodings (D-C)

The term encodings are `@xochi/spec`'s (`conformance/shielded.json` 0.9.0)
and Riddler's `Shielded.*` modules parse them identically; a value either side
refuses, the other refuses too.

| Member | Encoding | Source |
| --- | --- | --- |
| `network.aztecChainId`, `network.protocolVersion` | canonical decimal string; Aztec scalar: nonzero, below the BN254 modulus r. `protocolVersion` is the numeric Aztec rollup version | §7 `NetworkIdentity` |
| `network.rollupAddress` | `0x` + 40 hex, nonzero EVM address | §7 `NetworkIdentity` |
| `network.l1ChainId` | canonical decimal string, positive uint256 | §7 `NetworkIdentity` |
| `network.genesisOrNetworkDigest` | `0x` + 64 hex, nonzero. A corridor MANIFEST value, carried verbatim. The bridge refuses any value but its configured one (`network_mismatch`) | §7 `NetworkIdentity`; `PXE_BRIDGE_SETTLEMENT_CORRIDOR` |
| `network` (whole) | the §7 struct `NetworkIdentity(uint256 aztecChainId,uint256 protocolVersion,address rollupAddress,uint256 l1ChainId,bytes32 genesisOrNetworkDigest)`. Its `hashStruct` is the `network_identity_digest` both shielded domain salts fold in | `shielded.json` `networkIdentity` |
| `corridor.corridorId`, `corridor.manifestDigest` | `0x` + 64 hex (bytes32) | §7 `ShieldedCorridor` |
| `corridor.corridorRevision` | JSON integer, 1..2^32-1 (uint32) | §7 `ShieldedCorridor` |
| `recipient`, `token` | `0x` + 64 hex Aztec value: nonzero, below r. A 20-byte EVM address is refused, never padded | §7 typed encodings (`AztecField`) |
| `recipientDescriptorDigest` | `0x` + 64 hex, any bytes32 (zero admitted). It IS `ShieldedDestination.descriptorDigest` / `RecipientBinding.descriptorDigest`, copied verbatim from the enrollment; the bridge never derives or interprets it | `shielded.json` `recipientBinding` |
| `amount` | canonical decimal STRING, `0 < amount <= 2^128 - 1` (a JSON number is refused) | §7 `BaseUnits` |
| `validUntil` | JSON integer, unix seconds | bridge |

Hex is accepted in either case and lowercased before the fingerprint.

Every value in `PXE_BRIDGE_SETTLEMENT_CORRIDOR` (`corridorId`,
`corridorRevision`, `manifestDigest`, `genesisOrNetworkDigest`) is an operator
decision. Unset refuses every createNote (`corridor_unconfigured`, `/ready`
503); another corridor is `corridor_mismatch`, another network digest
`network_mismatch`, both before anything is prepared.

### Canonical vector

`docs/vectors/settlement-v2.json`, generated by `scripts/settlement-vectors.ts`
(`npm run generate:settlement-vectors`) and checked by
`tests/settlement-vectors.test.ts`. Riddler vendors the file and checks its
request builder against it; never compute the expectation on the consumer side
or hand-edit the JSON. It holds the HTTP shape of one `aztec_createNote`, its
canonical terms and fingerprint; `networkIdentity` (type string, typehash and
digest, equal to `@xochi/spec` fixture-a's `0xf5046ae3...e968`); inputs that
keep the fingerprint and single-change refusals; `createNote.result` and
`createNote.partialNote` (every intermediate value of the payout proof;
Riddler's `aztec_payment_proof.json` inputs); `retiredVersions`; and the
may-broadcast query and answers. Request values are the spec's
`recipientBinding` baseline fixtures, not a real corridor.

## Observations

| `state` | Broadcast? | Fields | Consumer response |
| --- | --- | --- | --- |
| `prepared` | no (journaled, unmarked) | `txHash, expirationTimestamp, hold: may_broadcast_unknown \| may_broadcast_denied \| interrupted` | hold; retry the same operation later; never refund |
| `not_submitted` | no | `reason, retryableAfterRevalidation` | `true`: retry the same operation; `false` (e.g. `validity_bound_passed`): revalidate/requote |
| `request_in_flight` | maybe | -- | wait, then read |
| `submitted_unknown` | maybe | `txHash, expirationTimestamp, reason` (`post_mark_failure`, `response_deadline`, `node_reports_dropped_or_unknown`, `node_read_failed`, `validity_bound_passed`, `expiration_passed`) | hold and reconcile; never replay it. Absence from one node is not proof that the transaction never reached another node or an earlier fork |
| `pending` | yes | `txHash, expirationTimestamp` | wait |
| `included` | yes | `txHash, expirationTimestamp, executionResult: success, blockHash, blockNumber, receiptStatus (proposed\|checkpointed\|proven), observedAt, effects {state, noteHashes, nullifiers}, partialNoteRandomness` | non-terminal; wait for `finalized` |
| `finalized` | yes | as `included`, `receiptStatus: finalized` (durably recorded) | delivery evidence (never "completed" alone) |
| `reverted` | yes, reverted | as `included`, `executionResult: reverted`; terminal only at `receiptStatus: finalized` | no payout only at finalized |
| `unknown` | maybe | `reason` | hold |

Effects are uninterpreted evidence; which element pays the signed recipient is
proven by `partialNoteRandomness`, never asserted by the bridge.

`not_submitted` reasons: the admission refusals (`corridor_mismatch`,
`network_mismatch`, `account_mode_mismatch`, `token_mismatch`,
`network_unreadable`, `may_broadcast_unconfigured`, `corridor_unconfigured`,
`limits: ...`), `validity_bound_passed` (not retryable), `expiration_passed`
(protocol expiration passed BEFORE Riddler was asked; retryable),
`expired_after_allow` (NOT retryable, below), `partial_note_randomness_unresolved`
(NOT retryable, "Partial-note randomness"), `prepare_failed`, and
`response_deadline` (retry the same operation).

**`expired_after_allow` is terminal for the operation id.** Riddler's `allow`
durably bound that txHash (D-A); a fresh proof carries a new hash, which
Riddler denies for good. Requote under a NEW operation id.

**The gate is the authoritative bound check, in two steps.**

1. After Riddler's answer and before the mark, the gate checks the clock
   against BOTH `validUntil` and the attempt's protocol `expirationTimestamp`.
   An unmarked attempt past either is recorded `not_submitted` and never
   marked.
2. After the mark, a separate SYNCHRONOUS final step (`BroadcastGate.beforeSend`)
   rechecks both, and the client calls `sendTx` in the same synchronous run.
   A marked attempt refused here is never sent and answers `submitted_unknown`
   (`validity_bound_passed` / `expiration_passed`), never `not_submitted`.

## Partial-note randomness

`Token.transfer_to_private(to, amount)` (`@aztec-labs` 6.0.0) hides the
recipient in a partial-note commitment and enqueues
`_finalize_transfer_to_private_unsafe(from, amount, C)`:

```
C = P2([to, r], 568912195)                                   DOM_SEP__PARTIAL_NOTE_COMMITMENT
N = P2([3, C, amount], DOM_SEP__NOTE_HASH)                   3 = Token.balances slot
S = siloNoteHash(token, N)
U = computeUniqueNoteHash(computeNoteHashNonce(nullifiers[0], i), S), some i < 64
validity nullifier = siloNullifier(token, P2([C, from], DOM_SEP__PARTIAL_NOTE_VALIDITY_COMMITMENT))
completion log (token, public) = [P2([C], 3372669888), 3, amount]
```

`r` is drawn by the sending PXE's `aztec_misc_getRandomField` oracle and kept
nowhere else. Every mined observation carries it as `partialNoteRandomness`
(`0x` + 64 lowercase hex). With it, anyone holding the signed `(to, token,
amount)` and the payout account (`from`) recomputes `U` and the validity
nullifier and requires them among the effects; a Poseidon2 opening of `C` to
another recipient is infeasible. `r` is never logged, audited or metered, and
appears in no error message.

**Capture.** While `createNote` proves, every value the oracle returns is
recorded into an AsyncLocalStorage scope around that one send
(`src/partial-note.ts`). After proving, the bridge reads `C` from the one
`_finalize_transfer_to_private_unsafe` call and selects the one captured value
with `P2([recipient, r]) == C`. None or more than one: nothing is journaled or
sent, and the operation is `not_submitted`, `partial_note_randomness_unresolved`,
not retryable (requote under a new operation id; treat as an SDK
incompatibility).

**Journal before broadcast.** `r` is written in the same SQLite transaction as
the prepared bytes (journal schema 3); a resend never re-proves. Before a
resend the client re-derives `C` from the journaled bytes and refuses unless
the journaled `r` opens it for the journaled recipient.

**Journaled identity before a resend.** The hash stored at the front of the
bytes is only a prefix. Before the randomness check and before Riddler is
asked, the client recomputes the hash from the bytes (`src/tx-identity.ts`)
and requires it to equal the stored prefix and the journaled `txHash`, and the
expiry inside the bytes to equal the journaled `expirationTimestamp`; the gate
repeats the comparison. Bytes that fail (or do not decode) are never sent:
the answer is `-32002` with `observation {state: "unknown", reason:
"journaled_bytes_mismatch"}`, the attempt stays `prepared`, and every retry
answers the same. Hold, never refund, and have an operator compare the journal
row with the bytes.

**Attempts journaled before v2** have no `r` (`NULL` after the schema 3
migration): an unmarked one is never sent and is replaced by a fresh proof
under the same operation (denied if Riddler had bound its hash, held
`prepared`); a marked one is observation-only and its mined observations carry
`partialNoteRandomness: null`. Riddler holds such a payout.

## Fingerprint

Bridge-owned: `0x` + SHA-256 over `pxe-bridge/settlement-fingerprint/v1` and
one `name=value` line per term in a fixed order, hex lowercased
(`src/settlement.ts`). Consumers compare it for equality and compare `terms`
field by field; nobody recomputes it. The canonical vector pins one value.

## May-broadcast query (bridge -> Riddler)

After the exact prepared transaction (bytes, hash, protocol
`expirationTimestamp`) is flushed and before the mark, the bridge `POST`s
`PXE_BRIDGE_MAY_BROADCAST_URL` (Riddler: `/shielded/may-broadcast`) with
`Authorization: Bearer <PXE_BRIDGE_MAY_BROADCAST_TOKEN>` (Riddler's
`SHIELDED_MAY_BROADCAST_TOKEN`) and body
`{version: "pxe-bridge.may-broadcast.v1", operationId, fingerprint, txHash}`.

- Only **HTTP 200** with `{version, operationId (echoed), decision: "allow"}`
  marks. Any other status (201/202/204 included), `deny`, `unknown`, a
  timeout (5 s), a transport error, a redirect, a malformed body or another
  `operationId` holds the operation `prepared`.
- **The link is HTTPS.** `https:` anywhere; plain `http:` only to a loopback
  host (`localhost`, 127.0.0.0/8, `[::1]`), in every `NODE_ENV`; no
  credentials in the URL.
- The mark and the rolling-spend row commit in one transaction. Once marked,
  the attempt is observation-only and is never sent again.

### Riddler's decision table

Riddler answers from the operation's captured admission (operation id + the
fingerprint of the admitted terms) and binds the first `allow` (D-A)
(`Shielded.Operations.may_broadcast/3`):

| Riddler holds for `operationId` | Asked with | Answer |
| --- | --- | --- |
| no admission (or it is unreadable / malformed) | -- | `unknown` |
| an admission for another fingerprint | -- | `deny` (logged at error: an incident) |
| the admission, no binding | -- | bind `{operationId, fingerprint, txHash}` durably, THEN `allow`; `unknown` if the bind cannot be made durable |
| a binding | the same fingerprint and txHash | `allow` (the bridge resending its exact journaled bytes) |
| a binding | another fingerprint or txHash | `deny` (logged at error: a bridge journal rollback or loss) |
| anything, but the lookup errs or exceeds Riddler's 2 s budget | -- | `unknown` |

`key_compromise` (withdrawing an admitted operation's permission) is not
implemented. After an `allow`:

| After `allow` | Bridge | Observation |
| --- | --- | --- |
| both bounds still open | mark, then the synchronous final check, then send | `pending` / `included` / ... |
| `validUntil` passed before the mark | not marked, not sent | `not_submitted`, `validity_bound_passed`, not retryable |
| protocol expiration passed before the mark | not marked, not sent; the hash stays bound at Riddler | `not_submitted`, `expired_after_allow`, not retryable: requote under a new operation id |
| either bound passed after the mark, at the final check | marked, not sent | `submitted_unknown`, reason naming the bound |
| the gate closed (request deadline) before the mark | not marked, not sent; the hash stays bound | `prepared`, `interrupted`. A retry re-asks with the same hash and is allowed again while the attempt is unexpired; once it has expired a fresh proof is denied (`may_broadcast_denied`), and the remedy is again a new operation id |

### Single-use may-broadcast and the rollback domain (D-A)

`<journal>.hwm` mirrors the journal generation and catches a lost, swapped or
partially restored FILE; it cannot catch a restored VOLUME, since both live
on it. The guarantee is Riddler's single-use binding on its own durable store
(`RECOVERY_STATE_BACKEND=redis` in production): a journal that has forgotten
an `allow` and re-proves the same operation produces a NEW txHash, Riddler
answers `deny`, and the operation is held `prepared` instead of paying twice.
Riddler never issues a different `operationId` for the same payout: its
operation id is persisted with the sent terms before the call
(`Shielded.Operations.record_sent/2`).

## Request deadline

One deadline bounds a whole `aztec_createNote` (`SETTLEMENT_DEADLINE_MS`,
145 s = the 150 s HTTP response deadline less 5 s): admission, cooldown,
proving, may-broadcast and send all spend it. Every Aztec JSON-RPC call has
its own aborting 10 s transport deadline; the server admits at most 16
concurrent backend leases, with a separate pool for `aztec_getSettlement`
reconciliation. When the deadline passes, the gate closes synchronously, so
nothing the request started can be marked afterwards. The HTTP response
deadline (`res.setTimeout`, 150 s) aborts the request's signal BEFORE the 504
is written. A caller that got a 504 reads `aztec_getSettlement` and retries
the same operation.

## Journal (`PXE_BRIDGE_JOURNAL`)

SQLite via better-sqlite3, `synchronous=FULL`, rollback journal,
`locking_mode=EXCLUSIVE` taken at open: a second process on the same file
refuses to start. Operations and attempts are never pruned. Schema 3 (#78)
adds each attempt's partial-note randomness; schema 1 and 2 journals migrate
at open, their attempts keeping `NULL`. A stored value that is not `0x` + 64
lowercase hex is `journal_inconsistent`.

**Permissions.** The journal holds signed transaction bytes. At open the
bridge creates it 0600, tightens an existing journal, its side files
(`-journal`, `-wal`, `-shm`) and `.hwm` to 0600, and refuses a directory
writable by group or others; failure is `JournalPermissionError`.

**Startup invariant.** Every operation's state must be one its attempts and
spend rows can produce: `prepared` = current attempt unmarked, no marked
attempt, no spend; `may_broadcast`/`finalized`/`reverted` = current attempt is
the one marked attempt, spend row present; `claimed`/`not_submitted` = no
marked attempt, no spend; every spend row belongs to a marked operation, holds
exactly the terms `amount` and carries the mark's `may_broadcast_at`; the
stored fingerprint is the fingerprint of the stored terms. A missing or
malformed transaction identity on a prepared or marked operation is
`missing_transaction_identity`; any other violation is `journal_inconsistent`.
If the window cannot be rebuilt, writes are disabled with
`spend_window_unreadable`.

Writes are disabled (recovery reads continue, `/ready` is 503, `/status`
stays liveness) on: `corrupt`, `rollback_detected` (generation below
`<journal>.hwm`, a different journal id, or the mark missing beside a used
journal), `empty_journal_for_existing_account` (see "Legacy drain and
adoption"), `legacy_audit_unresolved`, `account_mismatch`,
`missing_transaction_identity`, `journal_inconsistent`,
`spend_window_unreadable`, `unknown_schema_version`, `write_failed`. New and
unmarked `createNote` attempts are then refused `-32004`; marked operations
stay observation-only; `aztec_getSettlement` stays readable. None clears
itself: restore the exact journal, or reconcile and adopt a new one.

## Legacy drain and adoption (D-B)

A journal-era bridge always starts a FRESH journal. Beside an account that
already existed on chain that is the lost-journal case, write-disabled until an
operator adopts it:

- **The acknowledgement names this journal.**
  `PXE_BRIDGE_JOURNAL_ADOPT_ACCOUNT=<account>@<journal id>`. The refusal
  (`empty_journal_for_existing_account`, in the log and in
  `aztec_getSettlement`'s `journal.detail`) prints the exact value. It is
  spent once; a replacement journal has a new id. A bare `<account>` is
  refused.
- **The legacy audit log must be drained.** When `PXE_BRIDGE_AUDIT_LOG` is
  configured, adoption is refused (`legacy_audit_unresolved`) while that file
  holds any legacy line (`status` present) that is: an **unresolved key**
  (an `idempotencyKey` whose LAST legacy line is `submitting` or `unknown`,
  at any age); a **spend inside the last 24h** (`success`, `unknown` or
  `submitting`, keyed or not); or a line that cannot be placed. Journal-era
  lines (`observation`, no `status`) are ignored. A file that cannot be read
  refuses; a missing one does not.

Procedure:

1. Stop sending createNote to the legacy bridge and let in-flight requests
   finish (its response deadline is 150 s).
2. For every unresolved key, establish on chain whether the transfer landed
   (its `txHash` when logged; otherwise the account's notes/nullifiers), then
   APPEND one legacy line for the key with the outcome:
   `{"timestamp":"<now ISO>","method":"reconcile","idempotencyKey":"<key>","status":"success"|"error","amount":"<amount>","txHash":"<hash if any>"}`.
   Last line wins per key. A keyless `unknown` line stops blocking once it is
   older than 24h.
3. Wait until 24h after the last spend line, reconciliation `success` lines
   included.
4. Start the journal-era bridge with `PXE_BRIDGE_JOURNAL` on its volume. It
   refuses writes and logs the `PXE_BRIDGE_JOURNAL_ADOPT_ACCOUNT=<account>@<id>`
   value. Set exactly that, restart, confirm `/ready` is 200, then remove the
   variable.

Do not point `PXE_BRIDGE_AUDIT_LOG` somewhere else to get past the check.

## Liveness and readiness

| Endpoint | Auth | Answers |
| --- | --- | --- |
| `GET /status` | none, separately rate-limited | Public minimal **process liveness** only: 200 `{"status":"ok"}` with no Aztec RPC. Served while the wallet is still connecting. |
| `GET /ready` | Bearer `PXE_BRIDGE_API_KEY`, then its dedicated readiness limiter | Projection from the admission predicate: 200 iff `ready: true`, otherwise 503 with stable reasons. During startup 503 `initializing`. An observation exceeding 20 seconds returns 503 `readiness_observation_failed`; later probes share that still-running observation. Failed authentication is charged to the auth-failure limiter and exposes no state. |

Backend or body-intake saturation adds `backend_capacity_exhausted` and
returns 503 for new admission. `POST /api/recovery` requires
`PXE_BRIDGE_RECOVERY_API_KEY` before reserving body intake, accepts only
`aztec_getSettlement`, and has its own rate-limit and backend capacity.

The readiness projection carries the flat fields `ready`, `sendMode`
(`"spending_limit"`; Riddler refuses intake when it is absent), `nodeVersion`,
`l1ChainId`, `rollupVersion`, `accountAddress`, `accountClassId`, `token`,
`maxAmount` and `dailyLimit`, plus finalized reference, policy, inventory,
rolling-window, fee-runway, node and journal observations. xochimilco's
testnet gate compares every alias it knows (`account`, `address`,
`accountAddress`, `version`, `chainId`, `token`, ...) at the top level and
one object deep, so no field may reuse one of those names for anything but
its pinned value (`tests/readiness.test.ts`).

Point container restarts at `/status` and traffic/deploy gates at `/ready`.
Never restart merely because readiness is false. In Oxide mode `/ready` serves
the Oxide projection; see "Oxide readiness".

## Deployment

**Journal volume.** One persistent directory per bridge, owned by the bridge
user (uid 1000, `USER node`), mode 0700, bind-mounted read-write, never shared.
`PXE_BRIDGE_JOURNAL` names a file inside it (`settlement.sqlite`);
`<journal>.hwm`, the SQLite side files and the audit log live beside it. Keep
it off any backup or snapshot that is restored automatically and treat a
restore as an incident. One writer: never scale the service.

**Environment.**

| Variable | Value |
| --- | --- |
| `PXE_BRIDGE_JOURNAL` | `/var/lib/pxe-bridge/journal/settlement.sqlite` |
| `PXE_BRIDGE_AUDIT_LOG` | `/var/lib/pxe-bridge/journal/audit.jsonl` (same path the pre-journal bridge used) |
| `PXE_BRIDGE_SETTLEMENT_CORRIDOR` | the approved rev 1 corridor JSON |
| `PXE_BRIDGE_MAY_BROADCAST_URL` | `https://<riddler>/shielded/may-broadcast` |
| `PXE_BRIDGE_MAY_BROADCAST_TOKEN` | secret; Riddler's `SHIELDED_MAY_BROADCAST_TOKEN` for this environment; delivered like the other bridge secrets (tmpfs file read by the entrypoint), never in the compose file |
| `PXE_BRIDGE_JOURNAL_ADOPT_ACCOUNT` | unset; set once, per the adoption procedure |

Riddler's side: `SHIELDED_MAY_BROADCAST_TOKEN`, `SHIELDED_NAMESPACE` (distinct
per environment, shared by blue/green colours) and
`RECOVERY_STATE_BACKEND=redis`.

**Readiness.** Gate deploys and new settlement traffic on `GET /ready`. Keep
the container healthcheck on `/status`: a journal with writes disabled must
not restart the service, because `aztec_getSettlement` and marked-operation
observation remain available.

The predicate admits only spending-limit deployments with a deployment record.
It checks the configured/derived address and class, initialization and pause
state, permitted token, local/on-chain allowlist root and limits, the
contract's spend window, finalized token inventory, rolling-window headroom,
fee runway, journal write health and fence, network identity, node transaction
readiness, and synchronized retained history. One exact nonzero `finalized`
block number/hash anchors every observation; `proven` and `latest` are never
fallbacks. The finalized timestamp must be at most 7,200 seconds old and no
more than 300 seconds ahead of local time. Unknowns are explicit not-ready
reasons.

**Marked exposure.** A `may_broadcast` operation counts against inventory, the
contract window and fee juice until the finalized block's timestamp passes its
attempt's protocol expiration (at most 86,400 seconds from its anchor block):
past it the transaction either landed at or before the finalized block or
never will. Each observation checks up to eight unexpired marked operations
through the `aztec_getSettlement` node observation (`createLandedReconciler`),
resuming after the last one checked, within `RECONCILE_BUDGET_MS` (5 seconds);
only a finalized receipt records an outcome, and running out leaves the
operations counted. A terminal operation stays counted while its expiration is
not before the finalized timestamp and its recorded block is above the
finalized block. Both lookups use the `attempts_expiration` expression index.

**Admissible headroom** is the smaller of the bridge's own 24h window
(`rollingWindow.localHeadroom`) and the contract's
(`rollingWindow.onChainHeadroom`): `spend_buckets` and `spend_bucket` read at
the finalized reference and replayed through `advance_window` to the finalized
timestamp (`onChainSpent`), less marked exposure and in-flight reservations.
Zero is `spend_window_exhausted`; unreadable `spend_window_unknown`; a stored
bucket after the finalized one `spend_window_inconsistent`.

Required inventory is `reservations + admissible headroom + marked principal`.
Required fee juice is `(pre-mark in-flight reservations + marked operations +
ceil(admissible headroom / live max-per-tx)) * per-transfer fee limit` (SDK
gas limits times predicted maximum fees per gas). Concurrent admissions share
one chain observation; capacity is evaluated again in `runAttempt` against the
live window and journal, synchronously with the reservation, which also
refuses an amount above on-chain headroom (`spend_window_insufficient`).

Readiness loss blocks only new admission. A marked operation keeps its lookup
and observation path but is never replayed. An admitted `prepared` operation
keeps recovering: its may-broadcast query and resend are not gated on the
`/ready` verdict. It is held only while one of these holds:

| Hold (`data.reasons`) | Source |
| --- | --- |
| `journal_unwritable`, `writer_fence_lost` | local journal |
| `may_broadcast_unconfigured` | local configuration |
| `readiness_observation_failed` | no readiness projection at all, so inventory and the contract window are unread |
| `inventory_unknown` | the probe could not read the finalized public token balance |
| `network_identity_mismatch` | node identity vs the operation's `network` |
| `account_paused` | finalized `paused` read by the readiness probe |
| `allowlist_root_mismatch` | finalized on-chain root vs the configured tree the attempt was proven against |
| `spend_window_unknown`, `spend_window_inconsistent` | the probe could not read the contract's window, or read one ahead of the finalized block |
| `operation_inventory_insufficient` | finalized public token balance below the operation's amount plus marked principal and other reservations |
| `operation_fee_runway_insufficient` | finalized fee juice below one per-transfer fee limit for this operation, each marked operation and each other reservation |
| `operation_spend_window_insufficient` | the contract's window at the finalized timestamp cannot take the operation's amount on top of marked principal and other reservations |
| in-memory rolling window full | `TransactionLimits.reserve`; answered `prepared`, never re-proved |

An unread token inventory or contract window holds (a shortfall in either
reverts in public after the fee is paid); an unread fee juice balance does not
(Aztec 6.0.0 `GasTxValidator` refuses an underfunded fee payer without
charging it, but sending would still mark the operation). Past `validUntil`
the operation is `not_submitted`; past the attempt's protocol expiry a new
attempt is prepared.

## Recipient readiness attestations

`POST /api/attestation`, authenticated only by `Bearer
PXE_BRIDGE_ATTESTATION_API_KEY` (no other credential works there, and it works
nowhere else). 404 when every attestation setting is absent; any partial
configuration fails startup. Requires the main RPC credential, the journal,
the corridor, and either the spending-limit account with
`PXE_BRIDGE_ACCOUNT_DEPLOYMENT` or Oxide mode with `PXE_BRIDGE_ACCOUNT_ADDRESS`.

Only `aztec_attestRecipientMembership` and `aztec_attestRecipientDeployment`
are accepted. Both take exactly:

```json
{
  "descriptor": "<@xochi/signer RecipientDescriptor object>",
  "descriptorDigest": "0x<32 bytes>",
  "recipient": "0x<32 bytes>",
  "network": "<@xochi/signer NetworkIdentity object>",
  "corridor": {
    "corridorId": "0x<32 bytes>",
    "corridorRevision": 1,
    "manifestDigest": "0x<32 bytes>"
  },
  "recipientAuthorization": {
    "digest": "0x<32 bytes>",
    "signature": "0x<64-byte Aztec Schnorr signature>"
  }
}
```

as the `params` of a strict JSON-RPC 2.0 request. On success, `result` is the
exact signed Membership or RecipientDeployment record. A typed refusal is HTTP
503 with error code `-32010`, message `Readiness attestation refused`, and
`data: {signed:false, refusal}`. Consumers import the schemas from
`@xochi-fi/pxe-bridge/attestation`.

Every object is strict: source wallet/chain/binding identifiers, block
selectors, witnesses, salts, indexes and unknown members are forbidden.
Network and corridor are accepted only for comparison with local state; callers
cannot select the domain or observation. `@xochi/signer` validates the
descriptor, its digest, the derived recipient, the pinned `aztec-6.0.0`
class/profile/network and the Schnorr authorization first.

Membership is positive only when the durable snapshot's complete
`(address,index)` mapping equals the mapping that built the in-memory tree,
that tree reproduces the exact finalized root, and the recipient witness
verifies; negative only when the same snapshot/root proves absence.
RecipientDeployment is positive only for the exact descriptor recipient and
class in initialized finalized state; a different subject/class is a refusal.
Before either read, the bridge validates the recorded solver address, pinned
class, initialized state, synchronized history, exact nonzero finalized
number/hash, and the 7,200-second age / 300-second future-skew limits. Every
uncertainty returns the unsigned refusal.

Records are signed over `readinessDigest` by a dedicated secp256k1 key
(`PXE_BRIDGE_ATTESTATION_SECRET_ARN` in production, dev-only
`PXE_BRIDGE_ATTESTATION_SECRET_KEY`; may not equal any custody or bearer
value). Consumers verify with `verifyReadinessRecord`, `maxAgeSeconds: 7200`
and `maxFutureSkewSeconds: 300`.

**RootUpdate relay.** The journal stores the local allowlist snapshot identity
and the exact relay envelope, durable before HTTP send, with one idempotency
key across uncertain delivery. Every tick delivers pending envelopes in order,
even when the chain observation (20 seconds) or the enqueue fails. Only the
configured URL's own `204` is acceptance; redirects are refused. A new record
is enqueued when the finalized root differs from the latest envelope's, when
the corridor changed, when the latest `attestedAt` is 3,600 seconds old, and
once per process after restart (an undelivered envelope for the current root
is reused). Body: `{corridor_id,corridor_revision,record:<signed RootUpdate>}`
to `PXE_BRIDGE_ATTESTATION_RELAY_URL` / `_TOKEN` (HTTPS or loopback HTTP).
Audit output carries only method, outcome and typed reason.

The Worker keeps one RootUpdate per corridor and replaces it only from a
strictly higher `rootBlock`, so a CHANGED root is enqueued only from a
finalized block above the latest envelope's; until then the tick records
`retry` with `finalized_tip_not_advanced`.

### Oxide mode: the private allowlist (xochi#751, xochi#775 option a)

The Oxide sender is a stock SchnorrAccount 6.0.0 with no on-chain allowlist.
Its recipient policy is an operator-held set that stays private: no on-chain
root, no root or list in the manifest or any public repo, no public endpoint
serving either, no log line naming a member. The bridge holds the set as the
same seed-salted height-10 tree (`src/allowlist-tree.ts`) and signs Membership
and RootUpdate over its root in the record formats above:

- `PXE_BRIDGE_OXIDE_ALLOWLIST_SEED_FILE`: owner-only file containing the
  nonzero 32-byte hex seed below the BN254 modulus; must differ from
  `PXE_BRIDGE_ALLOWLIST_SEED` and the attestation key.
- `PXE_BRIDGE_OXIDE_ALLOWLIST_RECIPIENTS_FILE`: owner-only file containing
  JSON `[{address, index}]` (`"[]"` admits nobody). Both files are required
  in production; direct `..._SEED` / `..._RECIPIENTS` values are
  development-only. Configuration errors disclose no address, position,
  seed, set or root.
- Attestation in Oxide mode requires `PXE_BRIDGE_ACCOUNT_ADDRESS`. The
  finalized observation (`AztecClient.observeStandardAccountChain`) requires
  the sender published at the stock SchnorrAccount 6.0.0 class
  (`0x2f7d07db...9d15`) and initialized at the finalized reference
  (`account_class_mismatch`, `account_not_initialized` otherwise).
- The root is the private tree's; `rootBlock` is the finalized block at which
  the bridge held it. Membership is positive only for a listed recipient
  whose witness reproduces that root; an enrolled but unapproved binding
  stays `pending`.
- A fresh Oxide send to a recipient outside the set is refused
  `recipient_not_allowlisted` (permanent) before any read.
- **The settlement journal is a secret in Oxide mode.** `allowlist_snapshots`
  holds the set in clear and `root_update_outbox` the roots; keep it and its
  backups under the seed's custody. At startup an Oxide bridge prunes every
  snapshot except the current set's and the newest delivered RootUpdate's.
  Outbox ids are `<run>:<idempotency digest>`, never the root.

**Initialize the Oxide send journal exactly once, before funding or opening
intake.** On the first start only, mount its owner-only directory and set
`PXE_BRIDGE_OXIDE_JOURNAL_INITIALIZE=true`. Confirm `/ready` reports the
journal writable, stop, remove the variable, start again. A new journal without
that acknowledgement refuses writes. An existing high-water mark with a missing
database is rollback detection and is never overwritten. The journal is bound
at creation to the sender, OXDAI and the pinned deployment. Never use
initialization to recover a lost journal: restore the matched database and
high-water mark, then reconcile every ambiguous send.

**Live G2 approve/revoke control.** The static file and
`scripts/oxide-allowlist.ts` are bootstrap/offline-recovery inputs only.
Enable the controller only with the complete set (all Oxide-only; a partial
set, revision other than 2, missing attestations/journals/corridor, credential
alias or invalid URL/address refuses startup; all absent means dark):

- `PXE_BRIDGE_OXIDE_ALLOWLIST_CONTROL_URL`: the Worker's bridge control
  route; HTTPS or loopback HTTP.
- `PXE_BRIDGE_OXIDE_ALLOWLIST_CONTROL_TOKEN`: dedicated bearer of at least 32
  characters, distinct from every other credential, the K1 account key and
  the private allowlist seed.
- `PXE_BRIDGE_OXIDE_ALLOWLIST_ADMIN`: separately custodied EVM admin address.
- optional `PXE_BRIDGE_OXIDE_ALLOWLIST_CONTROL_INTERVAL_MS`, 1,000-300,000;
  default 10,000.

The bridge polls outbound, adds or removes exactly the Worker's named
recipient, chooses a private free position for an approval and builds a full
replacement without installing it. The Oxide journal first commits operation
id, action, recipient, previous/next roots, replacement, sequence and digest;
an exact replay returns the same proposal, anything else is refused. The
operator signs only the proposed digest with the admin; the bridge verifies
operation, sequence, digest and recovered admin, then in one SQLite
transaction advances the current set and marks the operation applied, and
only then installs the in-memory tree, records the snapshot and pushes the
RootUpdate. Ambiguous delivery is reconciled by repeating the exact retained
message. Control messages never carry the set, root, position or witness.
Archive and restore both journals' database/high-water-mark pairs together.

An approval does not make a binding ready until the normal Membership and
RootUpdate refresh succeeds. A revocation closes fresh admission immediately;
journaled send bytes keep their recovery semantics. Close intake and reconcile
admitted obligations before revoking; never resolve an ambiguous send by
revoking and paying again. For offline recovery, stop the bridge, restore the
journal, and use `scripts/oxide-allowlist.ts` only to reproduce the retained
set.

### G1: approving or revoking an Oxide recipient in production

The production image ships no `tsx` or `scripts/`, and the journal volume is
uid 1000 mode 0700. Use the tool image, built from the running bridge's tag,
as a one-off container that mounts the journal read-only with no network.

- **Host:** the mainnet sidecar host (`roles/xochi_aztec_sidecar` in
  DROOdotFOO/xochimilco), `ovh-solver`, journal at
  `/opt/xochi-aztec-sidecar/journal/settlement.sqlite`.
- **Secrets:** 1Password vault `Xochi Shielded Tracer`, item
  `<OXIDE_ALLOWLIST_ITEM>`, fields `seed` and `recipients`. The deploy role
  materializes them as 0600 mounted files. The seed, current set and change
  reach the container on **stdin only** (`--stdin`, KEY=VALUE lines): never
  as an environment variable or argument. The next set comes back on stdout
  into a 0600 file on `/dev/shm` (macOS: `mktemp` under `$TMPDIR`), goes
  into 1Password through a piped template, and the file is shredded.

```sh
# On ovh-solver, once per bridge release, from a checkout of the running image's tag:
git -C /opt/pxe-bridge-src fetch --tags && git -C /opt/pxe-bridge-src checkout <tag>
docker build --target oxide-allowlist -t pxe-bridge-oxide-allowlist:<tag> /opt/pxe-bridge-src

# Stop the bridge (the journal is locked while it runs).
ssh ovh-solver 'docker stop xochi-aztec-sidecar'

# From the control machine. A refusal stops here and NOTHING is written to 1Password.
set -o pipefail
ITEM='<OXIDE_ALLOWLIST_ITEM>'; VAULT='Xochi Shielded Tracer'
umask 077; next=$(mktemp /dev/shm/oxide-next.XXXXXX) || exit 1
trap 'shred -u "$next" 2>/dev/null || rm -f "$next"' EXIT
{
  printf 'PXE_BRIDGE_OXIDE_ALLOWLIST_SEED=%s\n' "$(op read "op://$VAULT/$ITEM/seed")"
  printf 'PXE_BRIDGE_OXIDE_ALLOWLIST_RECIPIENTS=%s\n' "$(op read "op://$VAULT/$ITEM/recipients")"
  # The change: ADD with an INDEX (random, or a free position), or REVOKE.
  printf 'OXIDE_ALLOWLIST_ADD=%s\n' "$(op read "op://$VAULT/$ITEM/next_recipient")"
  printf 'OXIDE_ALLOWLIST_INDEX=random\n'
} | ssh ovh-solver 'docker run --rm -i --network none --read-only --tmpfs /tmp --user 1000:1000 \
    -e PXE_BRIDGE_JOURNAL=/journal/settlement.sqlite \
    -e PXE_BRIDGE_ACCOUNT_ADDRESS=<OXIDE_SENDER_ADDRESS> \
    -v /opt/xochi-aztec-sidecar/journal:/journal:ro \
    pxe-bridge-oxide-allowlist:<tag> --stdin' > "$next" || exit 1
[ -s "$next" ] && jq -e 'type == "array"' "$next" >/dev/null || { echo "no set produced; nothing stored" >&2; exit 1; }

# Store it through a piped template (never as an argument: that puts the set in argv).
op item get "$ITEM" --vault "$VAULT" --format=json \
  | jq --rawfile v "$next" '(.fields[] | select(.label == "recipients") | .value) = ($v | rtrimstr("\n"))' \
  | op item edit "$ITEM" --vault "$VAULT" >/dev/null || exit 1
# The trap shreds $next. Then redeploy/start the bridge through the role.
```

`<OXIDE_SENDER_ADDRESS>` is the Oxide sender the deploy role sets as
`PXE_BRIDGE_ACCOUNT_ADDRESS` (the script refuses to add it). `next_recipient`
is a field the operator sets on the item for this one change; delete it
afterwards. A journal left with a hot rollback file after an unclean stop
cannot be opened read-only: start and stop the bridge once first. The script's
stderr names neither a recipient, a position, the set's size nor the root.

For a revocation, finish the drain first and send
`OXIDE_ALLOWLIST_REVOKE=<address>` (no `OXIDE_ALLOWLIST_INDEX`) instead. Then
redeploy the bridge and confirm the RootUpdate published (`[attestation]`
`{"method":"RootUpdate","outcome":"delivered"}`).

## Oxide readiness

With `PXE_BRIDGE_SEND_MODE=oxide`, `GET /ready` (same auth, limiter, 20-second
deadline and single flight) answers the Oxide projection
(`src/oxide/readiness.ts`). Riddler asks the same predicate before each fresh
send, passing the operation id so its own claim is excluded
(axol-io/Riddler#1437). It answers two questions:

- `ready` / `reasons`: **serving health only**. 200 iff `ready`, else 503.
  Riddler gates the payout of already-admitted orders on this alone. Reasons:
  `oxide_pins_unknown`, `oxide_pin_mismatch`, `oxide_l1_unknown`,
  `oxide_l1_not_pinned`, `oxide_portal_frozen`, `enclave_unreachable`,
  `enclave_attestation_refused`, `node_readiness_unknown`, `node_not_ready`,
  `journal_unwritable`, `attestation_unconfigured`, `corridor_unconfigured`,
  `network_identity_unknown`.
- `admission.freshSend` / `admission.reasons`: **capacity for one more new
  order**. `freshSend` is `ready` and no capacity reason. Reasons:
  `private_balance_unknown`, `journal_unreadable`,
  `private_balance_insufficient` (available is 0), `fee_runway_unknown`,
  `fee_runway_insufficient`, `spend_window_unknown`, `spend_window_exhausted`,
  and `backend_capacity_exhausted`. Riddler requires it for quotes, new
  reservations and the pre-pull check; it never affects resends.

Every Oxide fact that is READ is `{"state":"known", ...fields}` or
`{"state":"unknown","reason":"<reason>"}`; an unread value is never zero.
`journal` and `attestation` are local facts and carry no `state`.

```
{
  "ready": bool, "reasons": [string],
  "admission": {"freshSend": bool, "reasons": [string]},
  "observedAt": <unix seconds>,
  "sendMode": "oxide", "accountMode": "standard",
  "accountAddress": "0x<64 hex>", "token": "0x11d2bed2...e0a3",
  "oxide": {
    "corridor":       {"state":"known","corridorId":"0x<64 hex>","corridorRevision":<int>,
                       "manifestDigest":"0x<64 hex>"},
    "network":        {"state":"known","aztecChainId":"<dec>","protocolVersion":"<dec>",
                       "rollupAddress":"0x<40 hex>","l1ChainId":"<dec>",
                       "genesisOrNetworkDigest":"0x<64 hex>"},
    "privateBalance": {"state":"known","observed":"<dec>","syncedBlock":"<dec>","readAt":<unix seconds>,
                       "committed":"<dec>","committedSends":<int>,"available":"<dec>"},
    "feeRunway":      {"state":"known","observed":"<dec>","committed":"<dec>",
                       "committedSends":<int>,"perSendFeeLimit":"<dec>"},
    "caps":           {"state":"known","maxPerTx":"<dec>","dailyLimit":"<dec>",
                       "windowSpent":"<dec>","windowHeadroom":"<dec>"},
    "pins": {"manifest": {"state":"known","pinned":bool},
             "l1":       {"state":"known","pinned":bool,"portalFrozen":bool}},
    "enclave":        {"state":"known","attested":bool},
    "node":           {"state":"known","acceptingTransactions":bool},
    "journal":        {"writable":bool,"reason"?:string},
    "attestation":    {"configured":bool}
  }
}
```

A spending-limit bridge's projection carries `"sendMode": "spending_limit"`
at the same place. Riddler refuses intake when a full `/ready` projection
names no `sendMode`. The short-form 503s (`initializing`,
`api_key_unconfigured`, `readiness_observer_unconfigured`,
`readiness_observation_failed`) carry none.

| Fact | Source | Unknown reason |
| --- | --- | --- |
| `corridor` | `PXE_BRIDGE_SETTLEMENT_CORRIDOR`, the settlement v2 member names | `corridor_unconfigured` |
| `network` | The node's identity (`AztecClient.networkIdentity`) plus the corridor's `genesisOrNetworkDigest` | `corridor_unconfigured`, `network_identity_unknown` |
| `privateBalance` | The sender's PRIVATE OXDAI balance from its own PXE (OxideToken `balance_of`), with the PXE's synced block read before the call. `committed` is the payout principal of current attempts that read has not seen: prepared with open bounds, marked and not yet observed mined before expiry, or observed mined above `syncedBlock` (`OxideJournal.committedPrincipal`). `available = max(0, observed - committed)`. `readAt` is when the balance was read: a snapshot at most 10 minutes old is served while the PXE is busy proving. OXDAI base units | `private_balance_unknown`, `journal_unreadable` |
| `feeRunway` | `OxideSender.feeRunway`: fee juice balance, fee limits of attempts that may still land, the most one more send can cost. Fee-juice base units | `fee_runway_unknown` |
| `caps` | `PXE_BRIDGE_OXIDE_MAX_PER_TX` / `_DAILY_LIMIT` and the journal's marked spends in the rolling 24h | `spend_window_unknown` |
| `pins.manifest` | The published Oxide manifest and zk.money profile (`OxidePinChecker`) | `oxide_pins_unknown` |
| `pins.l1` | `assertL1Pinned` (chain, TeeRegistry PCR0 hash, CertManager root, portal token/registry/rollup/cap) and `OxidePortal.$frozen` | `oxide_l1_unknown` |
| `enclave` | The fleet's attestation, verified as a pin would (Nitro chain, pinned PCR0, registered keys) | `enclave_unreachable` (the fleet OR the L1 reads the check needs) |
| `node` | The node's `isReady` | `node_readiness_unknown` |
| `journal` | The OXIDE journal's health (`PXE_BRIDGE_OXIDE_JOURNAL`, `OxideJournal.health`) | -- (`journal_unwritable` on `reasons`) |
| `attestation` | Whether the attestation producer and RootUpdate publisher run | -- |

**Staleness.** On `/ready` a successful check is reused for up to 60 seconds;
a failure is never reused. `pins.manifest` can lag up to 6 minutes
(`OxidePinChecker` keeps a 5-minute cache under the 60-second one); `pins.l1`
and `enclave` up to 60 seconds. Admission (`admit`) and the sender's preflight
read L1 fresh. Runway, caps and journal are read on every call. The balance is
a snapshot: a call waits up to 2 s for the PXE, then serves the newest read at
most 10 minutes old, with `committed` recomputed against that snapshot's
synced block AND read time. A hung PXE balance call is never duplicated; once
its snapshot ages out, capacity stays unknown until it settles.

Admission for one fresh send of `X` (`OxideReadiness.admit`):

- **Refused (permanent):** a recipient outside the private set
  (`recipient_not_allowlisted`), `X <= 0` (`amount_invalid`),
  `X > 5,166 DAI` (`amount_over_note_max`), or `X > caps.maxPerTx`
  (`amount_over_per_tx_cap`; default 1,000 DAI).
- **Refused (permanent), the deployment is not the pinned one** (OX-6,
  xochi#744): the manifest or profile moved (`oxide_pin_mismatch`), L1 is not
  the pinned chain/registry/portal (`enclave_refused:l1_not_pinned`), or the
  enclave's PCR0 is not the pinned image hashing to `TeeRegistry.PCR0_HASH()`
  (`enclave_refused:pcr0_not_pinned` / `enclave_refused:pcr0_hash_mismatch`).
  The names are the sender's own preflight strings. Permanent for the
  OPERATION: Riddler refunds it. The bridge latches nothing; a failed check is
  never cached and the next fresh send reads again. The same conditions keep
  `ready` false. `attestation_invalid`, a frozen portal, a manifest or
  profile body that is not the file's shape (`oxide_pins_unknown`) and every
  unread fact stay transient.
- **Admitted** iff `ready` and `admission.freshSend` and
  `X <= privateBalance.available` and `X <= caps.windowHeadroom`. Anything
  else is `not_ready` with its reasons (transient).
- The sender then applies its own checks: the 5,166 DAI note max, its
  in-memory reservations in the window, and the exact fee limit.

State moves: `privateBalance.committed` grows at the journal CLAIM (by the
terms' `amount`, while `validUntil` is open); `feeRunway.committed` when the
attempt is prepared (by its fee limit); `caps.windowSpent` only at the
may-broadcast mark. A send admitted into a window another send then fills is
held `cap_window_full` at its own mark and resent once spends age out. A
Riddler reservation for an operation the bridge already journaled is also
inside `committed`, which only understates headroom.

Neither the allowlist, its root nor its size appears in the projection, and
readiness failures are logged by error class only.

## sendMode (0.4.0) and the Oxide payout proof (0.4.3, pxe-bridge#84/#94)

Every `aztec_createNote` names `sendMode`: `"spending_limit"` or `"oxide"`.
Missing, unknown, or `oxide` with `accountMode` other than `"standard"` is
refused at the schema (`-32602`, permanent). A bridge serves one mode
(`PXE_BRIDGE_SEND_MODE`); the other is refused before anything is claimed
(`-32602`, `send_mode_unsupported`), as is an oxide request for a token other
than the pinned OXDAI (`token_mismatch`).

- **Fingerprint:** `oxide` adds the line `sendMode=oxide` right after
  `accountMode=...`; `spending_limit` adds no line, so its fingerprint equals
  0.3.0's. Rows journaled before 0.4.0 carry no `sendMode`.
- **Oxide operations** live in the Oxide journal (`PXE_BRIDGE_OXIDE_JOURNAL`)
  under their v2 terms and fingerprint; may-broadcast is asked for that
  fingerprint, and the transfer's private `meta` carries it as the order
  fingerprint (`[sha256ToField("pxe-bridge/oxide-order-fingerprint/v1"),
  hi128, lo128, 0...]`). One operation id names one operation across both
  journals (a reuse is `-32003`).
- **Prepared commitment:** every Oxide `prepared` observation carries
  `payoutNoteCommitment: {scheme: "oxide-payout-note-v1",
  partialNoteRandomness, siloedNoteHash}`, from the exact transaction
  evidence journaled before may-broadcast; the bridge recomputes the siloed
  hash from the signed recipient, token and amount. A consumer MUST verify and
  durably bind this object with the prepared fingerprint, transaction hash and
  expiry before it authorizes broadcast or moves source funds. A missing,
  malformed, changed, or terms-inconsistent commitment is unknown, never
  admission.
- **Mined proof:** successful Oxide observations carry the committed
  randomness as `partialNoteRandomness` and `payoutNoteHashIndex`, the index
  in `effects.noteHashes` of its unique note hash. A finalized revert carries
  the same randomness and a null index only when effects are available and the
  committed note is absent at every index. A present or duplicated note,
  malformed or unavailable effects answers `unknown` /
  `payout_note_hash_unresolved`; unavailable effects are not recorded, so a
  later read retries. Spending-limit observations carry none of the
  Oxide-only fields.
- **Legacy attempts:** an Oxide transaction admitted without
  `payoutNoteCommitment` cannot prove non-payment. Consumers MUST keep its
  revert held.
- Oxide `prepared` holds use the v2 vocabulary (`cap_window_full`,
  `preflight_refused` surface as `interrupted`). The request deadline closes
